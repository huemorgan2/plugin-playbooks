## Learned

- Graph id rules as landed (`docs/v2.md` §6 carries the same text): `step-<call_site_id>`; containers `<if|for|while|try>-<first call-site id inside, document order>` with `_2`, `_3` on same-kind repeats; `gather-<first argument id>`; compute `compute-<next item node>` / `compute-end-<block id>`; block ids `run`, container node id for loop/try bodies (`orelse` appended), `if-<ref>-then` / `-else`, `try-<ref>-except-<i>` (1-based), `try-<ref>-finally`; `With` is transparent (its body is spliced into the enclosing block). No id ever derives from a line number; `node_ids` is pre-order (trigger nodes first).
- The trace overlay keys on the journal `id` + `occurrence` (both written by the loop); step rows are not read by the canvas. Status map `in_flight → running`, `done`/`failed_handled → done`, `failed`/`timed_out_unknown → failed`, `parked → waiting` (+ `parked_on`). A node's canvas status is its LAST row's status (a loop site that failed on occurrence 3 shows failed; the panel lists all three).
- `DbJournalStore.read` raises `KeyError` for a run with no rows — that is the "journal-less" branch of `get_run`, so pblang runs and a python run that died before entry 0 look the same to the UI (no `trace` key).
- `VersionDetail.format` (the version row's) drives the UI branch and wins over the editor-level `format` prop — the mixed case (python candidate beside a pblang live) renders each version with its own canvas path.
- The plugin/11 end-to-end script can assert the canvas server-side: `GET /playbooks/{name}/graph?version=<candidate>` → `node_ids` contains `step-<id>` for every call site the checker summary lists; `GET /playbooks/runs/{run_id}` of a journaled run → `trace[-1].node` is the failing site and `failed_line` the one-liner's line. No browser needed.
