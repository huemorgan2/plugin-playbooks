## Learned

1. **Template-rendering parity is real and the comparison absorbs it**: v1 renders every templated arg through Jinja (`runner.py:2198-2210` → `str(value)`), so a row's `inputs["body"]` for `body=fetch.result.rows` is the STRING `"[{'id': 1, 'q': 'x'}]"` while v2 passes the list. Without a rule every migrated playbook that forwards a step result would be an `args` mismatch. Rule landed in `_diff_paths` (migrate.py:247-270): a v1 string equal to `str(<v2 value>)` is the same arg; anything else is reported. This is M4 open item 15 (template-rendering parity, owner question) seen from the comparison side — the rule accepts, it does not hide: the `effects` key shows both forms.
2. The journal carries no gather membership; `v2_groups(code)` derives it statically from plugin/10's graph (`gather-<first argument id>` containers), the exact twin of the v1 `parallel` walk over the definition — so `compare` never depends on timestamps.
3. `wait_event` in a v2 journal has `name None` and the event in `args["name"]`; `approve`/`wait_event` rows on the v1 side carry no inputs, so the comparison for those kinds is kind + name only (documented in the module docstring). `subtask` compares `inputs` only (v2 args also carry `returns`, a projection).
4. `_stubs_from_recorded_run` already dedups the `<tool>#<n>` alias when the tool name equals the step id — a migrated playbook that keeps v1 step ids as `_id` gets `occurrences_unmatched == []` for free when the pblang step ids equal the tool names (as `mig` does); when they differ, the `<tool>#<n>` aliases show up as unmatched — that list is not a failure signal for the migration recipe, `comparison.match` is.
5. The luna tool runtime may pass boolean parameters as strings; `_flag` accepts both (Exit test 7 calls once with `True` and once with `"true"`).
