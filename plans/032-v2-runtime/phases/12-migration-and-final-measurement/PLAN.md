## Goal

Every live pblang playbook on the target agent is rewritten as a v2 (python-format) playbook by the agent, proven against its own last green live run by a dry run whose effects match, run once for real as a candidate, and published by the owner — one card per playbook — with a ledger row per playbook; the count at start and the final Success-criteria verdict (dojop/03) are recorded; the retirement of the v1 runner and `LANGUAGE_CHEATSHEET` is handed to the owner as a separate decision.

## Scope — changes

1. **Comparison helper** — new module `plugin_playbooks/v2/migrate.py` (an addition to the repo plan's proposed `v2/` layout; recorded in the summary):
   - `v1_effects(definition, rows) -> list[Effect]`: the effect sequence of a recorded **v1** run from its `playbook_step_runs` rows (`PlaybookStepRun` models.py:180-200: `step_id` :187, `step_kind` :188, `status` :189, `inputs` :190, `outputs` :191, `started_at` :195), ordered by `started_at` then primary key. One row exists per executed step, one per loop iteration (`_execute_step` runner.py:641-671 → `_create_step_run` :1360-1371 with `step_kind=step.kind.value` :1365; loop rows per iteration per the `_record_step_cost` docstring :1385-1387). Mapping from `StepKind` (definition.py:15-29): `tool_call` → `tool` (name = `outputs["tool"]`, args = `inputs` — the rendered args stored at :820/:664 with vault refs raw, :767-768), `llm_step` → `llm` and `agent_step` → `agent` (args = `{"prompt": inputs["prompt"]}`, stored truncated to 2000 chars at :1004 / :958), `wait_for_approval` → `approve`, `wait_for_event` → `wait_event` (name = the event), `subtask` → `subtask` (name = the playbook); `code`, `condition`, `parallel`, `loop`, `state`, `halt` contribute no effect (their children have their own rows). The n-th row of a step id becomes occurrence `<id>#<n>`. Rows of steps nested in a `parallel` container (resolved from `definition`) form an unordered group.
   - `v2_effects(journal) -> list[Effect]`: the same sequence from a dry run's `journal` (phase 05 result shape; entries `{kind, id, occurrence, args, ...}` per phase 06's `DbJournalStore.read` shape), skipping entry 0 (`kind="run"`) and the `now` / `random` / `log` kinds; `gather` children are individual effects, grouped unordered.
   - `compare_effects(v1, v2) -> {"match": bool, "v1_count": int, "v2_count": int, "mismatches": [...]}`. **Definition of "same effects with the same args"**: equal length, and at every position the same `kind`, the same `name` (tool name for `tool`, event for `wait_event`, playbook for `subtask`, none for `llm`/`agent`/`approve`) and equal canonical args, where canonical = `json.dumps(args, sort_keys=True, default=str)` after (a) dropping underscore-prefixed effect options (`_id`, timeout/retry options as phase 02/03 define them), (b) keeping `vault:<name>` strings literal (`_VAULT_REF_RE` runner.py:159; never resolved), (c) for `llm`/`agent` comparing only `prompt`, cut to 2000 chars on both sides. **Mismatch classes**, each with `position`, both sides, and for `args` the JSON-pointer paths that differ: `order` (same multiset, different sequence — checked first, so a reorder is one finding, not a cascade), `missing` (v1 effect with no v2 counterpart), `extra` (v2 effect beyond v1), `kind`, `name`, `args`. Any mismatch ⇒ `match: false`. Unordered groups compare as multisets.
   - `stubs_from_v1_run(rows) -> dict[str, Any]`: per-occurrence stubs keyed `<id>#<n>` for a v1 run: tool rows → `outputs["result"]` (the wrapper written at runner.py:878), llm/agent rows → `outputs` (the dict, or `{"_raw": ...}` :975 / :1018), approve rows → `{"approved": True}`, wait_event / subtask rows → `outputs`. Only `status == "done"` rows; a run that is not `status == "done"` or is a test run (`PlaybookRun.is_test` models.py:165; trigger `agent-candidate`, agent_tools.py:2699) is refused with an error naming the rule.
2. **Tool option** — `playbook_dry_run` (`_dry_run` agent_tools.py:1572-1633 as extended by plugin/05 and plugin/08) gains `compare: boolean` (default false). With `stubs_from_run=<run_id>` naming a run that has step rows but no journal entries (a v1 run), stubs come from `stubs_from_v1_run`; with `compare=true` the result gains `"comparison": compare_effects(...)` plus `"compared_run_id"`, `"compared_run_version"`. Dry runs still write no rows (phase 05 invariant). The parameter does not change tool count, policy or risk level (`tests/test_manifest_drift.py:50-60`), so no manifest change.
3. **The "last green live run" rule** (used by the helper and the ledger): the newest `playbook_runs` row of the playbook with `status == "done"`, `is_test` false, `playbook_version == live_version` (stamped at runner.py:416-418; `live_version` models.py:53), trigger any but `agent-candidate`. Found with `playbook_runs(name, version=<live>, status="done")` (`_runs_read` agent_tools.py:1369-1428, returns `is_test`) or `GET /playbooks/{name}/runs?version=<live>` (routes.py:965-990); its rows from `GET /playbooks/runs/{run_id}` (routes.py:993-1024, ordered by `started_at` :1003 — `playbook_status` :612-660 does not order, :618-620, so the helper orders itself).
4. **Migration ledger** — a markdown table in this phase's `execution_summary.md`, one row per live pblang playbook on the target agent: playbook · agent · v1 live version · last green live run id + date · v2 candidate version · dry-run comparison (`match` or the mismatch classes, helper output attached) · candidate run id + status · publish card id (`approval_id` in the `playbook_publish` result, `tests/test_repro_fixplaybooks_lifecycle.py:163`) · resulting live version (read back from `GET /playbooks/{name}` `live_version` routes.py:714) · outcome (`migrated` | `stays pblang: <reason>`).
5. **Where the migration runs** — the plugin is a branch build until M6, so fleet playbooks cannot be migrated in this phase (master §4). Assumption, owner to confirm (repo `PLAN.md` Risks 9; M5 "Decision flagged"): rehearsal on one `vaselin-*` agent with the phase-12 build side-loaded, then the real per-playbook fleet migration after M6 under the same owner approval, one owner publish per playbook, using the same recipe and ledger. Two rehearsal routes: **A** — a `vaselin-*` agent that already holds live pblang playbooks with green live runs (vaselin-scanny-2 has such history, `tests/test_repro_fixplaybooks_lifecycle.py:5-11`); **B** — copies of the fleet's live pblang playbooks, which needs an export/import path that does not exist at HEAD (routes.py has no export/import/bulk route; `POST /playbooks` :721-766 accepts a `definition` only, `PlaybookCreate` :538-544, creates it live as v1 :757 and copies no runs, so the "last green live run" evidence would be missing). Route B therefore means building `GET /playbooks/{name}/export` (playbook row, live version content, last green live run with its step rows — vault refs raw, no secrets) and `POST /playbooks/import` (creates the playbook, inserts the run + rows with `trigger="imported"`, `is_test` false) — proposed shape, built only if the owner chooses B.
6. **Final measurement** — dojop/03 runs the Success criteria against this phase's build; this phase records the verdict table verbatim and the `VERDICT` line, and hands the retirement of the v1 runner + `LANGUAGE_CHEATSHEET` (reference.py, `playbook_language_reference` agent_tools.py:1554) to a separate owner decision with the remaining-pblang count.
7. Tests: new `tests/test_v2_migration.py`; no other test file changes. Version stamps: no bump by default (a new parameter and a module change neither manifest nor UI — repo `PLAN.md` "Conventions"); if the owner picks route B the two routes are not tools either, so still no bump; the number the side-loaded build carries is recorded in the summary and must be above the managed 0.46.0 copy (dojoP `PLAN.md` "01" step 4).

## Risks and open questions

1. **Rehearsal route (owner decision)**: A (a `vaselin-*` agent with its own live pblang playbooks and run history) needs no new code; B (copies of fleet playbooks) needs the export/import pair in Scope 5 because no such route exists at HEAD and `POST /playbooks` copies no runs. The fleet migration happens after M6 under the same approval; its count is taken then.
2. **`stubs_from_run` on a v1 run** is this phase's assumption, not the master's text (which speaks of a journal): stub values come from step-row `outputs` (`{"tool","result"}` wrapper at runner.py:878; llm/agent dicts at :975/:1018). If plugin/08 built `stubs_from_run` without a seam for journal-less runs, the dispatch lands in `_dry_run` here.
3. **What "same effects with the same args" compares**: effects are `tool/llm/agent/approve/wait_event/subtask` only (`now`/`random`/`log`/compute excluded); llm/agent args are the prompt prefix (v1 stored 2000 chars, no schema); underscore options are ignored; the rewrite keeps v1 step ids as effect ids so occurrences align. A rewrite that legitimately reorders independent effects is an `order` mismatch and stays pblang unless the owner accepts the row with the finding attached (recorded, not silently passed).
4. **v1 `wait_for_approval` auto-approves (runner.py:1060-1069) and `wait_for_event` returns a stub immediately (:1071-1083)**: a v1 "green" run carries no real decision or event payload; the comparison holds (args, not results), but the real candidate run parks on these effects and the owner answers them; noted per playbook in the ledger.
5. **Count definition**: "live" = status `enabled` or `disabled` with a pblang live version (archived excluded), per target agent (M5 risk 1). The list route exposes no format at HEAD; the source used is recorded verbatim.
6. **No-evidence playbooks**: a live pblang playbook with no green live run of its current live version cannot be checked by the recipe; it stays pblang with reason `no-evidence` unless the owner runs it once for real first (side effects) — owner's call per playbook.
7. **Replaying recorded inputs** in the candidate run repeats the run's side effects (emails, tickets, chat messages); the owner confirms inputs per playbook. Vault refs in rows and evidence files stay `vault:<name>` (runner.py:767-768); credentials referenced by migrated playbooks must exist on the rehearsal agent for the candidate run — never printed or committed.
8. **Phase ordering with dojop/03** is circular at phase granularity; resolved as build → dojop/03 run → summary (Steps 8).
9. **Publish read-back**: the publish-verify P0 plan (`test_publish_success_carries_verified_readback`) may still be red; the ledger's live version is read from the row, not the publish result.
10. **Version stamp**: no bump assumed (no manifest/UI change); if route B adds routes only, still none; if the executor adds a tool instead of a parameter, bump the minor and regenerate `luna-plugin.toml`. The measured build's stamp is the ship version candidate — fixed at M6.
11. **Parallel groups**: v1 rows of parallel branches interleave by `started_at`; the helper needs the v1 `definition` (from the version row, `GET /playbooks/{name}/versions/{n}` routes.py:1116) to know container membership; v2 `gather` children are assumed journaled in start order and compared as a multiset.
